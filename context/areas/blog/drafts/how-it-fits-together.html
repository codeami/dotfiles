One captain, many crews, one chart room

How I fit Kun Chen's agent factory together with plain-file context, and how I keep the agents doing what I actually meant

Draft 2 · post 2 in the "everything is a file" series · review in Lavish

In the first post I argued that, in AI, everything is a file: write your goals, rules and context down once, in folders, and every tool reads the same thing. That covers what the agents know. It says nothing about how work actually gets done when several agents run at once, or how you notice when one of them quietly drifts from what you asked.

For that I use Kun Chen's open-source stack, built around a tool called FirstMate. This post is about how the two halves fit together, and how I check that the agents' intent still matches mine.

Neither half is enough alone. Context without a crew is a well-labelled empty kitchen. A crew without shared context is a busy kitchen where every cook has a different recipe.

2. The ship

Who does what?

FirstMate leans into a nautical theme, and it's a useful picture.

  • You talk to one agent, the first mate. You never juggle tabs.
  • Ships change code. Each works in its own isolated copy of the repo, so three can run at once without stepping on each other.
  • Scouts do research. Their output is a report file, never code (section 2c).
  • Secondmates are longer-lived teams for one domain, such as market or product research, each with their own memory folder. They inherit my shared preferences from the first mate as a read-only copy, and sit idle until the first mate routes work to them.

Every one of those roles reads the same map file at startup, through its own tool's link. Claude, Codex or Pi: same map, same rules.

2a. The layers underneath

What happens between "do this" and a pull request?

Two layers are worth calling out. The watcher is a plain bash loop, so watching the fleet costs no model tokens while nothing is happening; it wakes the first mate only for things like a finished task, a stuck window or a pull request ready to merge. The dispatch step is the only thing that writes a task's status record, which is why work started any other way is invisible to the fleet (section 3).

2b. Treehouse: a pool of clean copies

How do several agents work on one repo without stepping on each other?

Think of a tool library rather than a shop: you borrow a clean, fully set-up copy of the repo, work in it, and hand it back. The next task starts in seconds because the dependencies and build cache are still there. A ship's brief even tells the crewmate to check where it landed and stop if it's sitting in your own checkout.

2c. Scouts: the research layer

How does research happen without anyone writing code too early?

A scout is for investigation, diagnosis, planning or audits, and for any question where the answer could change whether or what to build. It works in a throwaway copy, and its only output is data/<task>/report.md. The reports I've had back so far compare FirstMate with Claude's own agent features, compare it with another orchestration framework, and look for prior art before a project started. Each one marks every claim by how it was established (checked in a source, measured, or judgement), so I know which parts I can repeat in public.

3. Who sees how much

How much context does each agent get?

Jake Van Clief's rule for folders is: read only what the task needs. FirstMate applies the same rule to agents. The orchestrator holds the wide view; each worker gets a narrow one.

Why not just use Claude's built-in subagents?

Claude Code can already spin up subagents with their own small context. FirstMate deliberately blocks that tool in its orchestrator, for a reason it learned the hard way: in one recorded incident, the orchestrator ran four workers as built-in subagents instead of real crewmates. The work was invisible to the fleet view, two workers died when the main session restarted, and the work was lost.

Rule of thumb: a subagent is a quick question to a colleague at the next desk; a crewmate is a job ticket with a name on it.

The catch: intent passes through a middleman

A crewmate's "user" isn't you. It's the first mate. Your intent reaches the crew only through the launch brief. That's the old telephone game: every hand-off is a chance for "keep it under ₹50k" to become "keep it cheap". The good news is that the brief is a file (data/<task>/brief.md), so you can read exactly what was handed on.

So a crash or restart costs nothing: the next session reads the files and carries on. One deliberate split: the map lives in a public repo, so it holds only rules. My personal preferences and priorities live in FirstMate's private data/ folder, and the map just points to them.

5. Keeping the model's intent aligned with mine

Did the agent do what I meant, not just what it heard?

No single tool answers that. Four checks at four time scales do.

Should they be one tool? I don't think so, and FirstMate's own research agrees. They hold different kinds of thing with different authority: /stow stores your words (preferences are kept for good; operational lessons expire unless re-confirmed); backpass edits rules, only with quoted evidence and your sign-off; a divergence log is the model's mistakes, which is evidence, not instruction. Merge them and a model's guess could end up with the authority of something you said. So they stay separate, and meet in one place: the morning review.

The drift idea comes from Kay Kumar's research tool Substrate, shown in Jake Van Clief's video. It maps what the user meant and what the model decided as two graphs, then lists the gaps. In this setup the cheapest version is one heading in the end-of-session notes: "where the AI went its own way".

6. Where Matt Pocock's skills fit

Not everyone needs a fleet. Matt Pocock's skills give one agent better habits instead, packaged as skills you install into a repo: npx skills@latest add mattpocock/skills, then /setup-matt-pocock-skills once per repo.

  • /grill-me: the agent interviews you about your plan until every open question is resolved.
  • /to-spec, /implement, /tdd, /diagnosing-bugs, /code-review, /domain-modeling.

Version 1.3 added three that land right on this post's themes: /implement-spec (a whole spec as a task graph, implementer subagents in their own worktrees, one integration branch: a small cousin of FirstMate), /retro (looks back at a session and suggests changes to the agent's environment, turning mechanical mistakes into automated checks: the same job as backpass from a different angle), and /pr (a pull-request description with the smallest diagram that explains it and a one-way/two-way door risk call).

  2. Subagents vs crewmates. /implement-spec uses built-in subagents, which FirstMate blocks in its orchestrator. Run it inside one crewmate's task, not from the first mate.

The one I'd try first is /grill-me: it catches intent drift before work starts, when it's cheapest.

7. The whole loop

8. What's still rough (honestly)

  • /stow only runs when I ask for it.
  • backpass is installed but, last I checked, not yet working against my Claude and Codex logins, so the weekly rule loop is manual.
  • Divergence tracking is one heading in a note, not a tool.
  • Chat apps (Claude.ai, Claude Desktop's chat) can't read any of these files, so I still paste context there.
  • When you tell Claude "remember this", it saves to its own private memory, which Codex and the other tools never see. For anything that should apply everywhere, the shared map is the place, and it changes only through review.

9. The takeaway

Kun Chen's stack decides who does the work and whether it's safe to ship. Plain files decide what every agent knows. Small, separate reviews (the brief, the pre-push gate, /stow, backpass) keep what the agents do close to what I meant, and every one of them leaves a file I can read.
